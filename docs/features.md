# Модулі підготовки й автоматизації (18.11.2026)

Шість модулів поверх ядра. Усі працюють **на явних правилах і без ШІ**; модель (якщо підключена) лише
перефразовує «Питання перевірки», а числа звіряються з оригіналом. Жоден модуль не оцінює людей
і не ухвалює рішень, які за методикою ухвалює посадова особа.

| Модуль | Для кого | Ендпоінти | Код |
|---|---|---|---|
| «Питання перевірки» | керівник перед перевіркою | `GET /campaigns/{id}/devils-advocate` | `services/devils_advocate.py`, `routers/insights.py` |
| Агент-черговий | кожна роль — своє (див. розділ 2) | `GET /agent/digest` | `services/watchdog.py`, `routers/insights.py` |
| «Що змінилося для нас» (нормативка) | керівник, комісія, аудитор | `POST /normative/analyze` | `services/normative.py`, `routers/normative.py` |
| Автопілот хвилі | адміністратор | `PUT/GET /campaigns/{id}/autopilot`, `POST /autopilot/tick`, `GET /campaigns/{id}/autopilot/report`, `GET /me/notifications` | `services/autopilot.py`, `services/lifecycle.py`, `routers/autopilot.py` |

## 1. «Питання перевірки»

Найнеприємніші питання зовнішнього аудитора (у стилі оцінювання НАТО Building Integrity) до результатів
закритої хвилі. Керівник готується до перевірки заздалегідь.

**Як працює.** 18 правил (`RULES`), кожне — умова на числах знімка хвилі, вага (наскільки болюче питання),
текст питання з підставленими числами, докази з шляхом до числа в результатах (`evidence[].path`), що
підготувати (`prepare`) і на який екран перейти (`link.view`). Питання сортуються за вагою, за рівної — за `id`:
той самий вхід дає той самий результат. Відповідь містить і перелік усіх правил (`rules`) для прозорості.

| Правило | Коли спрацьовує |
|---|---|
| `cut_by_facts` | самооцінку компонента обрізано фактами (S > F + 25) |
| `reliability_c` | достовірність індексу C |
| `low_fact` | об'єктивний показник на рівні 1–2 |
| `category_gap` | РГ і особовий склад розходяться > 25 балів |
| `suspiciously_perfect` | > 30% анкет групи лише з найвищими відповідями |
| `low_participation` | участь групи < 60% |
| `checklist_unconfirmed` / `checklist_not_started` | «повністю» без підтвердження / «підлягає впровадженню» |
| `declared_above_computed` | заявлений рівень вищий за розрахований |
| `critical_question` | питання анкети < 40 балів |
| `component_drop` / `growth_unconfirmed` | значуще падіння компонента / зростання з позначкою «перевірити дані» |
| `no_facts` | для компонента немає фактів |
| `measures_overdue` / `measure_no_effect` | прострочені заходи / виконаний захід без ефекту в наступній хвилі |
| `rejected_recommendation` / `accepted_without_measure` | відхилена рекомендація / прийнята без заходу |
| `risk_signal_growth` | кількість знайдених ризиків зросла |

**Модель (опційно).** `?rephrase=true` і підключений `LLM_BASE_URL`: модель робить формулювання гострішими.
Якщо в новому тексті є число, якого немає в правилі й доказах, лишається оригінал. Оригінал завжди повертається
в `original_question`, модель — у `rephrased_by_model`. Без моделі все працює так само.

**Приклад (демо, «Хвиля 2»).**

```json
{
  "n": 1, "id": "cut_by_facts:accountability", "rule_id": "cut_by_facts", "severity": 100,
  "category": "Факти проти самооцінки",
  "question": "Ви оцінюєте «Підзвітність» на 58,9 балів, а факти показують 18,8. Чому система, на вашу думку, краща, ніж кажуть дані? Наприклад, «підозрілі закупівлі розібрано» — лише 40%.",
  "why": "Самооцінка 58,9 знижена до 43,8: факти показують 18,8 (+25).",
  "evidence": [
    {"label": "«Підзвітність»: самооцінка", "value": 58.9, "text": "58,9", "path": "components.accountability.self_score"},
    {"label": "за фактами", "value": 18.8, "text": "18,8", "path": "components.accountability.facts_score"},
    {"label": "Підозрілі закупівлі розібрано", "value": 40.0, "text": "40% (48 з 120)", "path": "facts.procurement_flags_reviewed"}
  ],
  "prepare": "Пояснення розриву по кожному факту: що саме не розглянуто вчасно і чому; план, коли частка досягне наступного порогу.",
  "link": {"view": "compare", "ref": "accountability"}
}
```

Інші питання демо: достовірність C; КІ 96 з 168; закупівлі 48 з 120; повідомлення 71 з 86; 2 прострочені заходи;
4 пункти чек-листа «повністю» без підтвердження; зростання на 13,5 з позначкою «перевірити дані».

**Свідомо не робить:** не питає про конкретних людей, не порівнює підрозділи між собою.
Доступ: `admin`, `leader` (свій підрозділ), `auditor`, `department`. Запит пишеться в журнал дій.

## 2. Агент-черговий: «що впало, чому, як виправити»

Детермінований огляд стану. Кожен пункт: `severity` (`critical` / `warning` / `info`), `what`, `why` (правило й
числа), `fix` (кроки в системі), `link`. Загальний `status`: `ok` / `attention` / `critical`.

| Категорія | Що перевіряється |
|---|---|
| `drop` | компонент між двома останніми хвилями змінився більше ніж на 5 балів. **Чому:** внесок кожного джерела у зміну самооцінки `w·S тепер − w·S тоді` (ОС, РГ, експерти, чек-лист), зміна обрізання фактами, питання й факти, що впали найбільше |
| `rise` | те саме для зростання — що спрацювало |
| `process` | прострочені заходи; строк за тиждень; рекомендації без рішення; відкриті хвилі з участю < 60% за ≤ 3 дні до закриття; незавершений чек-лист |
| `technical` | ланцюжок журналу дій (критично), черга теми 2 з помилками, джерела фактів без даних > 3 міс., помилки автопілота, нерозглянуті знахідки модуля «Перевірки» |

**Кожна роль отримує лише те, що може виправити** (`watchdog.audience`), і `link.view` веде на екран цієї ролі:

| Роль | Пункти |
|---|---|
| `leader` | `drop:*`, `rise:*`, прострочені заходи і строк за тиждень (`tracker`), рекомендації без рішення (`recs`) |
| `admin` | технічні збої: тема 2 й автопілот (`manage`), знахідки «Перевірок» (`checks`), джерела фактів (без посилання: налаштування розгортання); низька участь і «динаміки ще немає» (`manage`); журнал дій (`audit`) |
| `auditor` | пошкоджений журнал дій (`audit`); незавершений чек-лист, якщо аудит серед `CHECKLIST_CONFIRMERS` |
| `department` | нічого: Департамент лише переглядає, тож `items: []`, `status: ok` |

Інформаційні пункти (`severity: info`: «падінь немає», «зросло на…», «строк за тиждень» тощо) повертаються лише
з `?include_info=true`; без нього їх немає і в `counts` (лише `critical`, `warning`) — на них спирається дзвоник.
Автопілот раз на день кладе уповноваженим підсумок їхніх пунктів у сповіщення, якщо `status ≠ ok`.

Приклад (`why` для падіння «Культури» після третьої хвилі): «чек-лист: −15,6 бала; робоча група: −15,6 бала.
Найбільше впало питання «Яку цінність відіграє доброчесність…» (−6,2)».

## 3. «Що змінилося для нас»: аналіз нормативного документа

Завантажуєте новий наказ чи редакцію закону (`.docx`, `.pdf`, `.txt`, `.md` або текст) — система показує, які
**пункти чек-листа** (Додаток Б), **питання анкет** (Додаток В), **заходи типового плану** (Додаток Д) і
**показники методики** він зачіпає.

**Як працює (RAG без генерації, локально):** документ ділиться на пункти й абзаци; слова зводяться до основи
(перші 6 літер, без стоп-слів); фрагменти й елементи бази — вектори TF-IDF; схожість — косинус. Збіг
показується при схожості ≥ 0,12 і щонайменше 2 спільних основах, разом із **спільними словами** і **фрагментом
документа** — тобто кожен збіг пояснюваний. Для пункту чек-листа додається його стан в останній хвилі.
Той самий документ дає той самий результат; зовнішніх сервісів і моделей немає (закритий контур).

Приклад (синтетичний наказ про конфлікт інтересів, викривачів, навчання й закупівлі): 4.1.2 і 4.1.1 «Запобігання
та врегулювання конфлікту інтересів» (спільні слова: врегулювання, конфлікту, інтересів), питання «Робота з
викривачами» (канали, викривачів, повідомлень), показник «Повідомлення розглянуто вчасно», 4.5.1 «Перевірка
контрагентів» (закупівель, перевірку, учасників).

**Свідомо не робить:** не змінює пунктів і анкет сам — лише пропонує, що переглянути. Документ не зберігається;
у журнал дій — назва, розмір і sha256.

## 4. Хвиля на автопілоті

План задається один раз: дата відкриття, дата закриття, поріг участі для дострокового закриття, частота нагадувань.
Далі кожен крок (`AUTOPILOT_INTERVAL_SECONDS`, у Docker 300 с; або вручну `POST /autopilot/tick`):

1. Чернетку з настанням дати **відкриває** — той самий шлях, що й кнопка (`services/lifecycle.py`): склад фіксується, журнал дій пише «система, via autopilot».
2. Кожні N днів кладе **нагадування всім учасникам** хвилі. Хто вже пройшов, ніде не відстежується, тож нагадування нічого не розкриває.
3. **Закриває**, коли настала дата або в кожній анкеті участь ≥ порогу (і ≥ k).
4. Після закриття: знімки, **Word-звіт за Додатком Г** (`GET /campaigns/{id}/autopilot/report`), сповіщення керівникам «N рекомендацій чекають рішення», учасникам — «узагальнені результати доступні», **черга заходів у тему 2** (якщо задано `THEME2_URL`).
5. Раз на день: оновлює **охоплення навчанням** з флешкарток і кладе адміністраторам підсумок агента-чергового.

**Свідомо не робить:** не приймає й не відхиляє рекомендації і не створює заходів — це рішення відповідальної
посадової особи. У тему 2 йдуть лише заходи, які створила людина.

Кожен крок пишеться в журнал автопілота (`GET /campaigns/{id}/autopilot` → `events`), а `plan` описує людською
мовою, що станеться далі.

## 5. Флешкартки доброчесності

5 колод, 27 синтетичних ситуацій із контексту ВВНЗ: конфлікт інтересів, подарунки, повідомлення про корупцію
(обов'язкові), закупівлі, академічна доброчесність. Картка: ситуація → перші кроки → чому → посилання на закон.
Зміст — `backend/app/seed/data/flashcards.json`; перед використанням у роботі звірити з чинною редакцією законів.

- Колода зараховується, якщо переглянуто всі картки (`seen`). Відповіді на окремі картки не зберігаються.
- «Пройшов навчання» — усі обов'язкові колоди за останні 365 днів.
- Свій стан бачить лише сама людина; керівник — агрегат `GET /learning/stats` з порогом k (поіменних списків немає).
- З цих даних рахується показник **`training_coverage`** (`source = learning`): X пройшли з Y учасників підрозділу.

## 6. Цифри в «Джерелах» з модулів системи

Додатки Б–Д містять **показники й пункти**, але не числа: числа беруться з обліку. Тепер у демо чотири з шести
показників рахує сама система:

| Показник | Звідки | Як |
|---|---|---|
| Декларації подано вчасно | модуль «Перевірки» | синтетичні декларації проходять правило строку подання |
| Можливі КІ розібрано вчасно | модуль «Перевірки» | правила конфлікту інтересів знаходять випадки, частину «розглянуто» |
| Підозрілі закупівлі розібрано | модуль «Перевірки» | синтетичні закупівлі проходять правила червоних прапорців |
| Охоплення навчанням | флешкартки | історія проходження колод (з поновленням щороку) |
| Повідомлення розглянуто вчасно | зовнішній реєстр (`reports`) | `POST /indicators` |
| Призначення з перевіркою | кадрова ІС (`atestat`) | `POST /indicators` |

Числа підібрано так, що індекс демо-хвиль той самий (40,2 → 53,7): декларації, КІ й закупівлі збігаються з
попередніми до одиниці, охоплення навчанням — 717 з 972 (73,8%, той самий рівень 3).

## Де модулі в інтерфейсі (frontend-proto, Integra)

- «Питання перевірки»: кнопка «Підготуватися до перевірки» на «Огляді» і у «Звіті» відкриває бічну панель із питаннями; кожне питання має «До числа» (розклад, порівняння чи динаміка за `evidence[].path`). Повний перегляд: екран «Питання перевірки».
- Агент-черговий: критичні пункти й попередження (до трьох) у блоці «Що потребує уваги» на «Огляді» з пігулкою серйозності й розгортуваним «Як виправити»; ті самі пункти в дзвіночку в шапці («Потребує дії»). Окремої вкладки немає, пункти «до відома» не показуються.
- Флешкартки: пункт меню «Навчання» для всіх ролей і картка «Навчання» в «Мої результати»; охоплення бачать ролі з доступом до `GET /learning/stats`.
- Автопілот: розділ вибраної хвилі в «Керуванні циклом» (уповноважений; старі посилання `#autopilot` ведуть туди). Окремого пункту меню для перегляду немає. Для закритої хвилі показано лише план кроків і журнал.
- Що змінилось: пункт меню «Що змінилось», екран «Що змінилось для нас». Збіги знаходять правила; ШІ за кнопкою «Підсумувати» пише чернетку висновку (лише для керівника, Департаменту й аудиту, з вимикачем ШІ).
- Сповіщення: дзвіночок у шапці.

Докладніше: `frontend-proto/README.md`, `docs/api/frontend-mapping.md`.

## Безпека: координатор

Окремо закрито ескалацію прав: координатор керує респондентами й керівниками, але не створює адміністраторів і
координаторів, не видає ці ролі, не змінює й не блокує їхні облікові записи і не скидає їм паролі (403). Собі —
лише ім'я й пароль. Тест: `test_killer_features.py::test_coordinator_cannot_escalate`.
