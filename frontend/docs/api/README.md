# API-контракт: пропозиція фронтенду

## Що це

Контракт це «меню» розмов між фронтендом і бекендом: які запити існують, що в них передавати і що приходить у відповідь.
Файл `openapi.yaml` описує це формально (OpenAPI 3.1, українською). З нього можна згенерувати типи для фронтенду
(`npm run api:types`, результат у `src/api/schema.d.ts`) і перевірити коректність (`npm run api:lint`).

Це **пропозиція** для узгодження. Усе, що позначено «узгодити», бекенд може змінити; тоді ми змінюємо контракт, а не гадаємо.
Числа в прикладах збігаються з демо-даними фронтенду (`src/demo/data.ts`): індекс 54,2, рівень 3, достовірність C.

Загальні правила: база `/api/v1`, JSON, дати ISO 8601, id рядками, помилки `{code, message, hint}`, анкети версійні.

## Інваріанти (не обговорюються)

Жоден запит не повертає окремі відповіді; групи менші за k (за замовчуванням 10, налаштовується адміністратором циклу) ніколи не повертаються (стан `hidden_below_k`, `fallbackScope` це батьківський підрозділ);
admin і commissioner не мають доступу до відповідей; commissioner не бачить хто і скільки пройшли; немає іменних
рейтингів; відправлення анкети не повертає і не зберігає ідентифікатор людини разом із відповідями.

## Питання до бекенду

Ми нічого не вигадували за вас. Відповіді потрібні на таке:

1. Як зберігати анонімність технічно: чи окремі таблиці «призначення» і «відповіді» без звʼязку? Чи потрібні жетони (одноразові коди)?
2. Механізм входу (пароль, SSO, відомчий каталог) і формат токена сесії.
3. Ролі `leader`, `observer`, `checklist_editor`, `checklist_approver`, `auditor` (наші пропозиції): чи узгоджуються з вашою моделлю?
4. Де живуть ваги питань усередині компонента: в анкеті (`QuestionInput.weight`) чи в налаштуваннях методики?
5. Чи рахує бекенд індекс, обмежувач і достовірність, чи їх рахує фронтенд за даними? Ми пропонуємо бекенд (одне джерело правди).
6. Як рахується хеш методики (що входить) і як перевіряється цілісність журналу (ланцюжок хешів?).
7. Як групи й підрозділи моделюються в структурі (`scope`): дерево вузлів, глибина, як визначається «підрозділ респондента» без розкриття особи?
8. Факти: які системи дають автоматичні дані, які лише ручний ввід, який графік оновлення?
9. У чек-листі «вніс» і «підтвердив» це посади чи імена? Що показувати в інтерфейсі?
10. Генерація PDF: на бекенді чи на фронтенді (друк)?
11. Пагінація й ліміти списків (зараз курсор лише в журналі).
12. Мінімальна група k: за замовчуванням 10; одне значення на цикл чи на категорію?
13. Підрозділи: дерево `Unit {id, name, parentId}`. Малі групи додаються до батьківського підрозділу (`fallbackScope`). Чи узгоджується це з вашою моделлю?

## Пріоритети для бекенду

1. **Проходження анкет і прийом відповідей** (група d, і анонімність): без цього немає даних.
2. **Dashboard** (`GET /dashboard`): головний екран, індекс, компоненти, достовірність.
3. **Розклад індексу** (`GET /index/breakdown`): прозорість методики, сума внесків = індекс.
4. **`/me`**: екран учасника зі станом `hidden_below_k`.
5. Далі: цикли й розсилка, анкети, факти й чек-лист, рекомендації й заходи, звіти й журнал, порівняння й динаміка.
